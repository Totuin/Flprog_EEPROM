# Аудит Flprog_EEPROM 1.0.1

**Результат:** кандидат для пользовательской компиляции, не утверждение об аппаратной проверке.

## Исправленные дефекты

1. `FlprogExternalEEPROM(size=0)` разыменовывал `_data[0]` при `_data == nullptr`.
2. Внутренние платформенные конструкторы создавали `_dataChanged[]` без инициализации, а `_data[1..]` содержал мусор, который мог записываться при первом запуске.
3. Многобайтовые методы проверяли `start+length` вместо включительного последнего адреса `start+length-1`, из-за чего последний доступный байт использовался не полностью; произведения `length*4` могли переполнять uint16.
4. Объекты EEPROM владели динамическими массивами, но не освобождали их; копирование могло привести к некорректному владению.
5. Внешний чип при I²C-сбое чтения маркера мог быть ошибочно принят за неинициализированный и перезаписан.
6. `pool()` внешнего чипа снимал флаг изменения даже при подтверждённой RT_HW ошибке операции.
7. Режим 24C0X без ограничения размера допускал обращение к адресам свыше 255 при однобайтовом протоколе.
8. Платформенные include использовали обратную косую черту.

## Не изменялось

- Публичные функции и протокол хранения значений. Старые имена с опечатками сохранены ради совместимости.
- Сторонние драйверы RT_HW, включая протоколы и базовые классы.
- Семантика `needUpdate`, `pool()`, маркера первого запуска и отложенной записи.
- `keywords.txt` — по итогам проверки корректен.

## Проверено

- Автономная сборка GCC C++11 для AVR, ESP32, RP2040, STM32 с `-Wall -Wextra -Werror`.
- Отдельная сборка Clang C++11 для ESP8266.
- Автономный запуск ASan/UBSan для AVR-ветки.
- Последний адрес диапазона, неверные адреса/длины, 16/32-битные числа, строки, пустые массивы, первый запуск, восстановление данных, ошибка I²C и её повтор, нулевой размер и предел 24C0X.

## Открытые вопросы

- На реальных платах нужны компиляция и аппаратная проверка корректной работы EEPROM, I²C и `commit`/`flush`.
- У ESP/RP2040 код не проверяет результат `commit()`. Его тип/семантика зависят от Arduino Core; без тестов конкретных платформ автоматический retry не добавлялся.
- На STM32 ветка использует `eeprom_buffered_*`; поддержка определяется выбранным STM32 Core.
- При ошибке чтения после маркера повторная инициализация требует явного вызова `begin()`; автоматическое восстановление не добавлялось.
- Двоичный формат 32-битных значений зависит от порядка байтов MCU; перенос данных между архитектурами может потребовать миграции.
